01 / LLM fundamentals

The model layer: how text becomes numbers, how a transformer processes context, how it generates output, and why model behavior is probabilistic rather than database-like.

Level 1Definition — what is an LLM?

A large language model (LLM) is a neural network trained on large collections of data to model sequences of tokens. Given preceding tokens, it estimates a probability distribution for the next token. Most modern general-purpose LLMs use transformer architectures.

Level 2What that means — the mental model

Think of an LLM as a learned pattern engine, not a person searching a library of facts. It converts input into token IDs, maps those IDs to vectors, processes the vectors through many neural-network layers, and predicts what token should come next. It then appends that token and repeats.

The model's parameters encode statistical relationships learned during training. The prompt supplies the immediate task and context. The runtime controls decoding, safety checks, tools, and delivery. These are separate parts of the product system.

Level 3Concepts in this space and what they are used for
Tokenization

Maps text to token IDs. Affects context usage, cost, truncation, and multilingual behavior.

Embeddings

Maps token IDs to learned vectors. Provides the numerical representation consumed by the network.

Transformer

Neural architecture built around attention and feed-forward blocks. Enables contextual sequence processing.

Self-attention

Lets tokens exchange information with other tokens. Used to model relationships across the input sequence.

Positional information

Encodes token order or position. Without it, sequence order would be ambiguous.

Weights and biases

Learned parameters. Determine the transformations applied to representations at inference time.

Context window

Maximum sequence budget supported by a model/request. Governs how much prompt, history, retrieval, and output can fit.

Decoding

Turns next-token probabilities into selected tokens. Greedy, sampling, temperature, and top-p affect output behavior.

Pre-training

Builds general representations and predictive capability from large corpora.

Post-training

Aligns behavior to instructions, preferences, and safety expectations.

Fine-tuning

Updates weights for specialized behavior, format, or task performance.

Inference

Runs the trained network to produce output. This is where serving latency and compute cost arise.

When to use what: prompt changes for task instructions; retrieval for fresh or private facts; fine-tuning for repeated behavior or format; a larger or reasoning-capable model when task complexity justifies the cost.

Level 4Engineering depth — what happens inside the model

From text to generated token

  1. Tokenize: A tokenizer segments input text into token IDs using a learned vocabulary.
  2. Embed: Each token ID is mapped to a vector representation; positional information is added or applied.
  3. Project to Q, K, V: Attention layers compute query, key, and value representations from hidden states.
  4. Attend: Queries are compared with keys; normalized attention weights combine value vectors. Causal masking prevents a position from seeing future tokens.
  5. Transform: Feed-forward/MLP blocks, residual connections, and normalization further transform each token representation.
  6. Predict: The final hidden state is projected to vocabulary logits, converted to probabilities, and decoded into a next token.
  7. Repeat: The generated token is appended and the decode loop continues until a stop condition or output limit.

Attention mechanics

For each attention head, the model computes query (Q), key (K), and value (V) matrices. A simplified scaled dot-product attention operation is: softmax(QKᵀ / √dₖ) V. Multiple heads learn different relationship patterns. The causal mask ensures autoregressive generation cannot use future tokens.

Training mechanics

  • Training examples are tokenized and passed through the network.
  • The model predicts target next tokens; cross-entropy loss measures prediction error.
  • Backpropagation computes gradients; an optimizer updates weights over many batches.
  • Distributed training partitions work across accelerators using data, tensor, pipeline, or expert parallelism.
  • Post-training may add instruction examples, preference comparisons, reward models, or policy optimization.

Inference performance

Prefill processes the prompt and builds attention state. Decode generates tokens sequentially. The key-value (KV) cache stores prior attention keys and values so they do not need to be recomputed for every new token. Long prompts increase prefill work; long outputs increase decode work; long contexts consume KV-cache memory.

Why the engineering details matter to a PM

  • Token count drives a large part of model cost and context pressure.
  • Model size, quantization, batching, and parallelism affect throughput and quality.
  • KV-cache capacity can constrain concurrency before raw compute is saturated.
  • Temperature changes sampling behavior, not the model's underlying knowledge.
  • Model/version, tokenizer, system prompt, and decoding settings should be recorded for reproducibility.

Key questions to be able to answer

Why does an LLM hallucinate?

Because next-token training rewards plausible continuation rather than guaranteed truth. Reduce risk with grounding, source citations, constrained outputs, verification, calibrated uncertainty, and abstention.

Why isn't an LLM a database?

Weights are distributed learned parameters, not structured, transactionally updated records. Use a database or API as source of truth; use the model to interpret, synthesize, or explain retrieved data.

What does temperature control?

It rescales logits before sampling. Lower temperature concentrates probability on likely tokens; higher temperature increases diversity. It does not raise factual accuracy.

02 / Tools, agents & MCP

The action layer: how an LLM interacts with software, data, and workflows—and how to build reliable systems around those interactions.

Level 1Definition — tools, agents, and MCP

A tool is an application capability exposed to a model through a structured interface. An agent is a system that uses a model to pursue a goal through iterative decisions and actions. MCP (Model Context Protocol) is a standard protocol for connecting AI applications to external tools and context providers.

Level 2What that means — model proposes, software disposes

The model normally does not execute an API call itself. It chooses a declared tool and produces arguments. The host application validates the request, checks identity and permissions, runs the operation, and returns the result. The model can then reason over that result and continue.

An agent adds a control loop: observe state, choose the next action, execute, inspect the outcome, and decide whether to continue, recover, or stop. MCP standardizes how capabilities and context can be presented to compatible clients; it does not automatically make a tool safe or trustworthy.

Level 3Concepts in this space and what they are used for
Tool schema

Name, description, and typed input parameters. Helps the model select a capability and form arguments.

Function calling

Structured model output requesting an application function. Used for APIs, calculations, and actions.

Orchestrator

Host-side controller that executes tools, manages state, retries, and routes results.

Agent loop

Repeated model/action/observation cycle. Used for multi-step tasks and adaptive workflows.

State

Current task progress and intermediate results. Enables continuation, recovery, and auditability.

Memory

Persistent or session-level information. Personalizes or resumes work; requires lifecycle and privacy controls.

Guardrails

Input/output checks, policy enforcement, and action constraints. Reduce unsafe or invalid behavior.

Human approval

Explicit confirmation before consequential actions such as sending, purchasing, or deleting.

MCP server

Exposes tools, resources, or prompts to an MCP client.

MCP client

Connects an AI host to an MCP server and negotiates capabilities.

Resources

Context or data exposed through MCP. Useful for documents, records, and reference material.

Tool permissions

Scopes what an agent can read or change. Supports least-privilege design.

Level 4Engineering depth — contracts, execution, and safety

Tool-call lifecycle

  1. Register tool metadata and a machine-readable argument schema.
  2. Include only relevant tools in the model request; tool overload can degrade selection.
  3. Receive a structured tool call and parse it strictly.
  4. Validate types, ranges, required fields, identity, authorization, and business rules.
  5. Apply idempotency keys and approval gates for side-effecting operations.
  6. Execute with timeouts, rate limits, and bounded retries.
  7. Normalize the result, remove secrets, and return a compact observation to the model.
  8. Trace the decision, call, result, latency, and failure without logging unnecessary sensitive data.

Designing schemas

Use narrow, unambiguous names; descriptions that explain when the tool should and should not be used; enums for constrained choices; explicit date/time formats; and required fields only when truly mandatory. Validate again in application code: model-generated JSON is untrusted input.

Agent control loop

Define a maximum step count, token/cost budget, deadline, allowed tool set, and terminal conditions. Detect repeated calls and loops. Persist checkpoints for long-running tasks. Separate planning from execution where the action is consequential. Make cancellation and recovery first-class behaviors.

Reliability and security

  • Prompt injection: Treat retrieved content and tool output as data, not privileged instructions.
  • Confused deputy: Execute using the user's authorized identity and scope, not a broad service credential by default.
  • SSRF/data exfiltration: Restrict destinations and returned fields.
  • Replay/duplicate action: Use idempotency and operation IDs.
  • Partial failure: Track which steps committed; compensate or expose partial completion clearly.
  • Audit: Record actor, intent, approval, tool, arguments (redacted), result, and timestamp.

MCP engineering considerations

MCP provides a common protocol surface, but production readiness still depends on transport, authentication, authorization, capability discovery, schema compatibility, server trust, versioning, and operational monitoring. A protocol standardizes the connection; it does not standardize the quality or safety of every connected service.

Agent versus chatbot?

Ask whether the system can autonomously choose and sequence actions, observe outcomes, maintain task state, and recover—not simply whether it has a tool button.

Why can a vague tool description be dangerous?

The model may choose it incorrectly or supply ambiguous arguments. Poor contracts increase invalid calls, retries, and unintended side effects.

03 / RAG & context engineering

The knowledge layer: connecting a model to current, private, attributable information without pretending that the model weights are a live source of truth.

Level 1Definition — what is RAG?

Retrieval-augmented generation (RAG) is a pattern in which an application retrieves relevant information from external sources and supplies it to a language model as context for generating a response.

Level 2What that means — separating knowledge from reasoning

The model provides language understanding and synthesis. A retrieval system finds relevant source material. The application combines the two so answers can reflect private, recent, or domain-specific knowledge and can point back to evidence.

RAG is not simply “put documents in a vector database.” It is a data pipeline, search/relevance system, context-construction problem, and generation/evaluation problem. The weakest stage can dominate end-to-end quality.

Level 3Concepts in this space and what they are used for
Ingestion

Connects to source systems and extracts content for indexing.

Parsing

Extracts text, structure, tables, and metadata from source formats.

Chunking

Splits content into retrieval units while preserving meaning and references.

Embedding model

Maps text to vectors for semantic similarity search.

Vector index

Supports nearest-neighbor search over embeddings.

Keyword/BM25 search

Finds lexical matches; useful for exact names, codes, and phrases.

Hybrid retrieval

Combines lexical and semantic candidates to improve coverage.

Reranker

Re-scores candidate passages for query relevance.

Metadata filters

Constrain results by tenant, time, document type, or access scope.

Grounding/citations

Connects generated claims to source passages for verification.

Query rewriting

Reformulates ambiguous or conversational queries for retrieval.

Context assembly

Selects and orders evidence within token and latency budgets.

RAG, fine-tuning, or prompt? Prompt for instructions; RAG for external and changing knowledge; fine-tune for stable behavior, style, or task patterns. Combine them when each solves a distinct problem.

Level 4Engineering depth — from source system to grounded answer

Offline ingestion path

  1. Connect to authoritative sources with least-privilege credentials.
  2. Extract documents and preserve source ID, owner, tenant, ACL, timestamps, and version.
  3. Parse content, retaining headings, table relationships, page references, and document hierarchy.
  4. Normalize, deduplicate, classify, and apply data-quality checks.
  5. Chunk by semantic boundaries; attach metadata to every chunk.
  6. Generate embeddings with a versioned embedding model.
  7. Write vectors and searchable text to indexes; record ingestion status and source version.
  8. Incrementally update changed content and propagate deletions or permission changes.

Online retrieval path

  1. Authenticate the user and determine the effective access scope.
  2. Interpret the query; optionally rewrite, expand, or decompose it.
  3. Run lexical, vector, or hybrid retrieval with security filters applied.
  4. Merge candidates and rerank them against the query.
  5. Deduplicate, diversify, and select evidence based on relevance and coverage.
  6. Fit selected passages into the context budget, retaining provenance.
  7. Generate an answer with instructions to use evidence and signal missing support.
  8. Validate citations and claims; return answer plus source links.

Engineering choices and trade-offs

  • Chunk size: Small chunks improve focus but can lose context; large chunks preserve context but dilute relevance and consume tokens.
  • Overlap: Helps preserve boundary information but increases index size and duplicate retrieval.
  • Embedding choice: Evaluate domain language, multilingual coverage, dimensions, latency, and index cost.
  • Hybrid weighting: Tune lexical/vector fusion against real queries; do not assume vector search always wins.
  • Freshness: Use event-driven updates or short sync intervals where source changes matter.
  • Security: Apply ACL filters before content reaches the model; post-filtering alone can leak restricted data into prompts or logs.

Measure each stage independently

Retrieval: recall@k, precision@k, MRR, nDCG, and ACL correctness. Generation: claim support, citation precision, answer relevance, abstention quality, and unsupported-claim rate. System: ingestion lag, index freshness, p95 latency, tokens per answer, and cost per successful task.

What are the two major RAG failure modes?

Retrieval failure (the evidence is not found) and grounding failure (the evidence is found but the answer does not faithfully use it). Diagnose them separately.

When is RAG overkill?

When a deterministic query/API, a small stable prompt context, or the model's general capability already meets the requirement more simply and safely.

04 / Orchestration & routing

The workflow layer: coordinating models, tools, state, and decisions while balancing control, flexibility, latency, and cost.

Level 1Definition — orchestration and routing

Orchestration is the control logic that coordinates model calls, tools, data, and workflow steps. Model routing is the decision process that selects which model or execution path should handle a request.

Level 2What that means — the conductor, not the instrument

The model is one component in a larger application. Orchestration decides what context to send, which capability to invoke, what to do with results, whether to retry, and when to stop. Routing decides whether a task goes to a fast/cheap model, a stronger model, a specialized model, or deterministic code.

Frameworks can simplify stateful flows, but they do not remove the need to understand the underlying control plane. An abstraction is useful when it makes the workflow easier to reason about, test, and operate.

Level 3Concepts in this space and what they are used for
Workflow graph

Nodes represent operations and edges represent transitions. Useful for branching and cyclic workflows.

State machine

Explicit states and transitions. Useful for predictable lifecycle and recovery.

Planner

Breaks a goal into steps. Useful when tasks require sequencing or decomposition.

Router/classifier

Classifies task or complexity to choose model, tool, or path.

Fallback

Alternative model or path when the primary route fails or exceeds limits.

Retry/backoff

Recovers from transient failures while avoiding retry storms.

Checkpoint

Persists progress so long-running tasks can resume after interruption.

Parallel execution

Runs independent tasks concurrently to reduce wall-clock time.

LangChain

Provides integrations and abstractions for common LLM application components.

LangGraph

Supports stateful graph orchestration and controlled loops.

Budget policy

Constrains time, tokens, tool calls, and spend per task.

Routing policy

Encodes quality, latency, privacy, availability, and cost requirements.

Level 4Engineering depth — workflow execution and model selection

Reference execution architecture

  1. Accept request; authenticate user and resolve tenant and policy context.
  2. Classify intent, risk, modality, complexity, and required capabilities.
  3. Select a route using explicit rules, a classifier, or a learned router.
  4. Assemble context and execute a model or deterministic step.
  5. Validate structured output and determine the next workflow transition.
  6. Invoke tools or parallel branches with bounded concurrency.
  7. Persist state/checkpoints and emit trace events.
  8. Apply terminal checks, response shaping, and user-visible completion status.

Model-routing decision variables

  • Task quality threshold and error cost.
  • Input modality and context length.
  • Latency SLO, throughput, and current provider capacity.
  • Price per input/output token and expected token volume.
  • Data residency, privacy, and model availability requirements.
  • Tool-calling reliability, structured output support, and safety behavior.

Cost and latency mechanics

Measure end-to-end cost per successful task: model tokens, embedding/reranking, tools, retries, orchestration, storage, and human review. Latency includes queueing, network, prefill, decode, tool execution, and serial dependencies. Parallelism reduces wall-clock time only when branches are independent and capacity is available; it can increase total compute and coordination overhead.

Framework versus raw SDK

Use a raw SDK for a small, linear flow where explicit code is easiest to inspect. Consider a framework when state, branching, persistence, retries, and human hand-offs become reusable infrastructure. Evaluate debuggability, observability, upgrade risk, vendor coupling, and the ability to inspect every transition.

How do you route at millions of calls?

Use task-aware routing, quality gates, fallback paths, and per-route telemetry. Optimize cost per successful task rather than simply sending every request to the cheapest model.

05 / System design & trade-offs

The product architecture layer: choosing the right combination of models, conventional software, data, infrastructure, and human judgment to solve a real user problem.

Level 1Definition — AI system design

AI system design is the end-to-end design of a product capability that uses one or more AI models alongside software, data, infrastructure, and operational controls to achieve a user or business outcome.

Level 2What that means — start with the job, not the model

The first question is not “which LLM should we use?” It is “what user task is failing today, and what capability would improve it?” Then determine whether AI is necessary, what level of autonomy is appropriate, what errors cost, and what constraints apply.

A product architecture may combine rules for policy, databases for truth, classical ML for prediction, an LLM for language tasks, retrieval for evidence, tools for action, and humans for judgment or approval.

Level 3Concepts in this space and what they are used for
Problem framing

Defines user, job, pain, frequency, and value before choosing technology.

Functional requirements

Describe what the system must do and the workflow it supports.

Non-functional requirements

Latency, availability, scale, privacy, security, and accessibility constraints.

Build/buy/fine-tune

Selects hosted model, self-hosting, or weight adaptation based on needs.

Hybrid architecture

Combines deterministic code, ML, LLM, retrieval, and human review.

Inference capacity

Maps traffic, token lengths, concurrency, and SLOs to accelerator requirements.

Prefill/decode

Separates prompt processing from token generation for performance planning.

GPU memory

Holds weights, activations, and KV cache; often a key capacity constraint.

Batching

Combines requests to improve accelerator utilization while managing latency.

Quantization

Uses lower-precision representations to reduce memory and sometimes improve throughput.

Fallback design

Provides degraded but useful behavior when model/tool paths fail.

Human-in-the-loop

Places review or approval where risk, ambiguity, or impact justifies it.

Level 4Engineering depth — architecture, capacity, and failure design

Example: summarize unread messages

  1. Resolve user identity and mailbox/message permissions.
  2. Fetch unread messages and thread context from authoritative APIs.
  3. Filter duplicates, classify relevance, and prioritize important items.
  4. Build a context package with source IDs, timestamps, and thread relationships.
  5. Call a suitable model with a bounded summary schema and evidence instructions.
  6. Validate output structure and check citations against retrieved messages.
  7. Present summary, source links, and actions separately; never silently perform consequential actions.
  8. Collect corrections and usage signals to improve the evaluation set.

Capacity estimation for 10 million users

Estimate daily active users × requests per user × input/output tokens, then model peak-to-average ratio and concurrency. Benchmark tokens/sec per accelerator at the target model, context length, batch size, and latency. Account for prefill/decode balance, KV-cache memory, model replicas, tensor/pipeline parallelism, utilization headroom, redundancy, and regional capacity. Convert required throughput into accelerator-hours and fully loaded cost.

GPU serving mechanics

  • Weights: Model parameters must fit in accelerator memory or be sharded/offloaded.
  • KV cache: Grows with active sequences, context length, layers, and attention heads; can cap concurrent sessions.
  • Batching: Improves utilization but may increase queueing and tail latency.
  • Quantization: Reduces bytes per parameter and memory traffic, with possible quality/accuracy trade-offs.
  • Parallelism: Tensor parallelism splits layer computation; pipeline parallelism splits model stages; data parallelism replicates models/requests.
  • Networking: Multi-GPU execution may depend on high-bandwidth, low-latency interconnects.

Failure and degradation strategy

Define behavior for model timeout, rate limit, malformed response, tool outage, retrieval miss, stale source, and partial completion. Use bounded retries, circuit breakers, fallback models or deterministic paths, queue limits, cancellation, and human escalation. Make degraded states visible to users instead of presenting partial output as complete.

06 / Evals, metrics & observability

The quality and operations layer: measuring whether an AI system works for real users, diagnosing why it fails, and preventing regressions as models and data change.

Level 1Definition — evaluation and observability

Evaluation is the systematic measurement of model or product behavior against defined criteria. Observability is the ability to understand the internal state of a running system from its emitted traces, metrics, and logs.

Level 2What that means — quality is a product property

A model benchmark is not the same as product success. The feature may produce fluent answers while failing the user's task, missing important cases, taking too long, or eroding trust. Evaluate the full workflow and segment results by user, task, risk, and operating condition.

Because model outputs are variable, evaluation often measures distributions and pass rates across repeated runs rather than exact string matches. Offline tests catch regressions before release; online monitoring detects changes in real traffic.

Level 3Concepts in this space and what they are used for
Golden dataset

Versioned representative examples used for repeatable regression testing.

Rubric

Explicit criteria for scoring correctness, relevance, completeness, and safety.

Precision

Of predicted positives, fraction that are truly positive; important when false positives hurt.

Recall

Of actual positives, fraction found; important when missing cases hurts.

F1

Harmonic mean of precision and recall; balances the two but hides their individual trade-off.

LLM-as-judge

Uses a model to score outputs against a rubric; scales review but needs human calibration.

Human evaluation

Expert or user review for nuanced quality and high-impact cases.

Faithfulness

Measures whether generated claims are supported by supplied evidence.

Retrieval metrics

Recall@k, precision@k, MRR, and nDCG assess retrieval and ranking.

Tracing

Connects model calls, retrieval, tools, and workflow steps for diagnosis.

Online signals

Edits, retries, abandonment, acceptance, escalation, and user ratings.

Drift/regression

Detects quality changes due to models, prompts, data, traffic, or dependencies.

Level 4Engineering depth — build the evaluation and telemetry loop

Evaluation pipeline

  1. Define user outcome, risk tiers, and failure cost.
  2. Sample real tasks; de-identify and curate representative cases.
  3. Label expected properties and evidence; document adjudication rules.
  4. Build deterministic validators for schema, permissions, calculations, and policy.
  5. Use human raters for nuanced dimensions; measure inter-rater agreement.
  6. Use LLM judges only after calibration against human ratings; test judge bias.
  7. Run repeated trials for stochastic behavior and report confidence intervals or pass-rate distributions.
  8. Set launch thresholds, segment-level guardrails, and rollback criteria.
  9. Run shadow/canary experiments, then monitor online quality and feedback.

Testing pyramid

  • Unit: Parsing, schema validation, access checks, deterministic business logic.
  • Component: Retrieval, tool adapters, prompt/context construction, model wrappers.
  • AI eval: Golden cases, adversarial prompts, repeated runs, rubric scoring.
  • End-to-end: Complete user workflows with realistic dependencies.
  • Production: Quality, cost, latency, errors, drift, and user outcomes.

Observability schema

Trace request ID, user/tenant scope (appropriately protected), model and version, prompt template version, token counts, context sources, retrieval scores, tool names and outcomes, latency by stage, retries, errors, estimated cost, safety interventions, and feedback. Avoid logging raw sensitive prompts or documents unless there is a justified, access-controlled retention policy.

Diagnosing a quality drop

Segment the drop by task type, user cohort, model route, geography/region, language, and release version. Compare model, prompt, retrieval index, source freshness, tool behavior, traffic mix, and evaluator version. Determine whether the issue is retrieval recall, ranking, context assembly, model reasoning, output validation, or UX before selecting a fix.

Offline pass, unhappy users

Check whether test cases represent actual workflows; whether users can discover and understand the feature; whether latency interrupts the task; whether answers omit context users consider obvious; whether trust and control are adequate; and whether the metric rewards a proxy instead of the outcome. Add user-derived cases to the evaluation set.

08 / Technical AI PM answer framework

The meta-skill: translate engineering depth into product judgment. A strong answer is not a list of technologies; it is a defensible decision.

1 · User problem

Who is the user, what job are they trying to do, and why is AI useful?

2 · Mechanism

What happens under the hood, from input to output?

3 · Alternatives

Could rules, search, conventional ML, or a smaller model do the job?

4 · Trade-offs

What are the implications for quality, latency, cost, privacy, and complexity?

5 · Failure modes

How can the system fail, and how will users recover?

6 · Evaluation

How will you know it works across realistic scenarios?

7 · Operations

How will you monitor, secure, scale, and improve it?

8 · Business outcome

What measurable customer or business value does it create?

Practice discipline: For every answer, be able to draw the architecture, explain one level below each box, name the top two failure modes, state the key metric, and explain the trade-off you would make first.

Suggested study sequence

  1. LLM fundamentals and model behavior.
  2. Tool calling, agents, and MCP.
  3. RAG, embeddings, and context engineering.
  4. Orchestration, routing, and system design.
  5. Evaluation, observability, and responsible launch.
  6. Practice end-to-end product design and cost estimation.
