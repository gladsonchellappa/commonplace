# AI PM Knowledge

A practical study guide for product managers building AI-powered products. Use the questions as interview prompts, but focus on being able to explain the underlying mechanisms, make trade-offs, and connect technical choices to customer outcomes.

## 1. LLM fundamentals

### How an LLM works

A large language model is a neural network—usually a transformer—trained to predict the next token in a sequence. Text is tokenized, converted into vectors, processed through layers of attention and feed-forward networks, and used to produce a probability distribution over the next token. Generation repeats this process until a stopping condition is reached.

**Core concepts**
- **Tokens:** Units of text processed by the model. A token may be a word, part of a word, punctuation, or whitespace.
- **Embeddings:** Dense numerical vectors representing tokens or other content in a learned semantic space.
- **Attention:** Lets each token incorporate information from other relevant tokens in the context.
- **Weights:** Learned numerical parameters that encode patterns acquired during training. They are not a searchable store of facts.
- **Context window:** The maximum amount of input and generated content the model can consider in one request. When content exceeds it, some information must be omitted, compressed, or retrieved selectively.
- **Next-token prediction:** The model predicts a distribution for the next token; decoding selects or samples a token, which is appended to the sequence.

### Training stages

- **Pre-training:** Learns broad language and world-pattern representations from large datasets, commonly using next-token prediction.
- **Post-training:** Shapes the pretrained model for useful behavior through techniques such as supervised fine-tuning, preference optimization, and safety training.
- **Fine-tuning:** Further trains model weights on a targeted dataset or task. It changes model behavior but is not the same as supplying live facts.
- **Prompting:** Changes the instructions and context for a request without changing model weights.

### Temperature and decoding

Temperature changes the sharpness of the token probability distribution during sampling. Lower values make high-probability tokens more dominant; higher values increase variety and unpredictability. Temperature 0 is typically close to greedy decoding, although implementation details can still matter. Temperature does not make a model more knowledgeable.

### Why models hallucinate

A model is optimized to generate plausible continuations, not to guarantee that every statement is true. It can lack relevant knowledge, misread ambiguous context, rely on weak patterns, or confidently fill gaps.

**PM response:** Ground answers in trusted sources, constrain the task, expose uncertainty, validate important claims, and provide abstention or escalation paths. Measure factuality and impact in the product's real usage context.

### Why an LLM is not a database

A database stores and retrieves records with explicit schemas and query semantics. Model weights encode statistical patterns, not a reliable, current, row-addressable source of truth. Use databases for authoritative structured records; use retrieval or tools to bring relevant data into a model request.

### Why identical prompts can produce different answers

Sampling, nondeterministic hardware execution, serving infrastructure, model/version changes, hidden system context, and tool results can all affect outputs. Reproducibility requires controlling as many of these variables as possible and recording model and configuration versions.

## 2. Tools, agents, and MCP

### Tool and function calling

A model generally does not execute an external function by itself. It emits a structured tool request; the application validates and authorizes it, executes the function, and returns the result to the model. The model can then interpret the result and continue.

**Typical flow**
1. The application sends messages and available tool definitions to the model.
2. The model requests a tool with a name and structured arguments.
3. The orchestrator validates arguments, permissions, and policy.
4. The application executes the tool and returns its output.
5. The model uses the result to formulate a response or request another tool.

### Tool definitions and descriptions

A tool definition usually includes a name, a natural-language description, and an input schema. The description helps the model decide when the tool is appropriate; the schema constrains the arguments. Vague descriptions, overlapping tools, or permissive schemas make selection and execution less reliable.

### Prompt, tool, and skill

- **Prompt:** Instructions and context for a model invocation.
- **Tool:** A callable capability that performs an action or retrieves information.
- **Skill:** Reusable domain instructions, procedures, and supporting knowledge that guide how work is performed. A skill may teach an agent when and how to use tools.

### Agent versus chatbot

A chatbot primarily responds to user turns. An agent can pursue a goal over multiple steps, maintain state, choose tools, observe results, recover from failures, and decide when the task is complete. The boundary is a spectrum: adding a tool call alone does not necessarily make a system meaningfully agentic.

### Agent memory

Memory may include short-lived conversation state, persistent user preferences, task state, or an external knowledge store. Decide what should be remembered, for how long, how it can be corrected or deleted, and what permissions govern its use. Do not treat the context window as durable memory.

### MCP

The Model Context Protocol (MCP) is an open protocol for connecting AI applications to external tools and context providers through a standardized interface. It can reduce bespoke integration work, but it does not eliminate the need for authentication, authorization, input validation, observability, versioning, and security review. Compare MCP with a one-off API integration based on ecosystem reuse, interoperability, operational overhead, and control requirements.

## 3. RAG and context engineering

### Retrieval-augmented generation (RAG)

RAG retrieves relevant external information and supplies it to the model as context, helping it answer using data that may be private, changing, or absent from model training.

**Typical RAG pipeline**
1. **Ingest:** Connect to source systems and extract documents.
2. **Prepare:** Clean, normalize, split, and enrich content with metadata and access controls.
3. **Chunk:** Divide content into retrieval-sized passages while preserving useful semantic boundaries.
4. **Embed and index:** Convert chunks into vectors and store them alongside metadata, often in a vector-capable search system.
5. **Retrieve:** Embed the query and find candidate passages using vector, keyword, or hybrid search.
6. **Rerank and filter:** Improve relevance, apply permissions, and remove unsuitable results.
7. **Assemble context:** Select passages, citations, and instructions within the token budget.
8. **Generate:** Ask the model to answer using the supplied evidence.
9. **Evaluate and observe:** Measure retrieval quality, groundedness, latency, cost, and user outcomes.

### RAG versus fine-tuning versus prompting

| Approach | Best suited for | Main limitation |
|---|---|---|
| Prompting | Instructions, formatting, examples, task framing | Does not reliably add large or frequently changing knowledge |
| RAG | Current, private, source-grounded information | Retrieval can miss, mis-rank, or return poor evidence |
| Fine-tuning | Consistent behavior, style, task patterns, specialized formats | Updating facts is costly and knowledge may not be reliably retrievable |

These approaches can be combined. For example, fine-tune for a consistent output format, retrieve current policy documents, and prompt the model with task-specific instructions.

### Vector databases and embeddings

A vector database stores embeddings and supports similarity search. It is useful when semantic similarity matters, but vector search is not automatically the best retrieval method. Keyword search is often better for exact identifiers, names, and codes; hybrid search combines strengths.

### Chunking

Chunk size and overlap influence retrieval precision, context cost, and whether a passage contains enough surrounding meaning. Chunk by document structure where possible; preserve titles, headings, source IDs, timestamps, and access metadata. Evaluate chunking choices against representative queries rather than choosing a universal size.

### Frequently changing information

Use authoritative source connectors, incremental ingestion, freshness metadata, deletion propagation, and cache invalidation. For rapidly changing or transactional facts, call the source system at request time instead of relying solely on an asynchronously refreshed index.

### Two broad RAG failure modes

1. **Retrieval failure:** Relevant evidence is not found or is ranked too low.
2. **Generation/grounding failure:** Evidence is retrieved, but the model misinterprets it, ignores it, or makes unsupported claims.

Diagnose these separately. Improving the model will not fix a broken retrieval pipeline, and improving retrieval will not guarantee faithful generation.

### Context engineering versus prompt engineering

Prompt engineering focuses on the wording of instructions. Context engineering designs the full information supplied to the model: system instructions, conversation state, retrieved evidence, tool outputs, memory, ordering, metadata, and token allocation.

### When RAG is overkill

RAG may be unnecessary when the task uses a small, stable set of facts, a deterministic API can answer directly, the model already has sufficient general knowledge, or the cost and complexity outweigh the value. Prefer the simplest architecture that meets accuracy, freshness, privacy, and latency requirements.

## 4. Orchestration and routing

### Orchestration

Orchestration coordinates models, tools, data, and workflow steps. It manages sequencing, state, retries, timeouts, branching, permissions, and failure handling.

### LangChain and LangGraph

LangChain provides abstractions and integrations for building LLM applications. LangGraph focuses on stateful, graph-based orchestration, including cycles and more controlled agent workflows. Choose based on the workflow's complexity and the level of control required—not framework popularity.

### Raw SDK versus framework

A raw SDK call can be simpler, more transparent, and easier to optimize for a small workflow. A framework can help when integrations, state management, branching, or reusable orchestration become substantial. Abstraction adds value only when it reduces total complexity; it can otherwise obscure behavior and make debugging harder.

### Model routing

A router selects a model or execution path based on task characteristics such as complexity, modality, latency target, cost budget, privacy constraints, and quality requirements. A classifier may route by intent or difficulty; policies can also use explicit rules, confidence, and fallback paths.

### Unit economics of routing

At high call volumes, a small per-request cost difference compounds. Measure total cost per successful task, not just cost per token. Include retries, tool calls, retrieval, guardrails, evaluation, caching, and human review. Routing to a cheaper model is useful only if quality and completion rates remain acceptable.

### Four useful layers of an AI product stack

1. **Experience:** User interface, workflow, and feedback.
2. **Orchestration:** Prompts, context assembly, routing, tools, and agent control.
3. **Intelligence:** Models, embeddings, rerankers, and evaluation models.
4. **Data and infrastructure:** Sources, indexes, storage, compute, security, and observability.

This is a practical mental model, not a universal industry standard.

### Multi-agent systems

Use multiple agents when roles require distinct context, permissions, tools, or independently verifiable responsibilities. Avoid splitting work into agents merely for novelty. Define ownership, hand-offs, shared state, termination conditions, and conflict resolution. Parallel agents can increase latency, cost, and coordination failures.

## 5. System design and product trade-offs

### Design an AI feature: summarize unread messages

Start with the user problem: help someone catch up quickly without missing important information. Define the target user, message sources, freshness needs, and what counts as a useful summary.

A high-level design might include:
- A permission-aware message retrieval service.
- A prioritization step to select relevant unread messages.
- A summarization model with citations or links to source messages.
- A UI that distinguishes facts, inferred themes, and suggested actions.
- Feedback controls and a way to inspect the original messages.

Define success through time saved, useful coverage, factuality, trust, and follow-through—not summary length alone. Test edge cases such as long threads, conflicting messages, attachments, and access changes.

### Latency, quality, and cost

These objectives compete. Larger models and more retrieval or reasoning steps may improve quality but increase cost and latency. Set a product-level quality threshold, then optimize within it using routing, caching, smaller models, parallelism, shorter context, and selective tool use. Track p50 and p95 latency, cost per successful task, and quality together.

### Build, buy, or fine-tune

- **Buy/use a hosted model:** Fastest path to capability; assess data handling, reliability, cost, customization, and vendor dependency.
- **Build/self-host:** More control over deployment, data, and optimization; requires model-serving expertise and infrastructure operations.
- **Fine-tune:** Consider when repeatable behavior or task performance cannot be achieved economically with prompting and retrieval. It is not a default solution for keeping facts current.

### Why not use an LLM for everything?

LLMs are probabilistic and can be expensive, slow, and difficult to validate. Use deterministic code, databases, rules, and conventional ML when they solve the problem more reliably. A hybrid system often offers the best product experience.

### Why XGBoost over an LLM for tabular prediction?

For structured, labeled tabular data, gradient-boosted trees such as XGBoost can be more accurate, cheaper, faster, and easier to evaluate than a general-purpose LLM. Use an LLM when language understanding, unstructured context, or natural-language interaction is central. The choice should follow data and task characteristics.

### Hybrid AI systems

A hybrid system combines deterministic software, conventional ML, LLMs, retrieval, and human judgment. For example, rules can enforce eligibility, a classifier can prioritize cases, an LLM can summarize evidence, and a human can approve a high-impact decision.

### GPUs and cost structure

GPU cost is influenced by accelerator type and count, memory capacity and bandwidth, utilization, model size, sequence length, batching, parallelism, serving overhead, power, networking, and availability. For inference, distinguish prefill (processing input tokens) from decode (generating output tokens). Capacity planning should model traffic shape and latency SLOs, not just average tokens per day.

### Estimating inference cost for 10 million users

Do not estimate from user count alone. Build a workload model:
- Active users per day and requests per active user.
- Input and output tokens per request, including retrieved context.
- Peak-to-average traffic and concurrency.
- Model mix, routing, caching, retries, and tool-call rates.
- Throughput per accelerator at the target latency and quality.
- Replication, redundancy, utilization headroom, and serving overhead.

Then estimate accelerator-hours and multiply by the fully loaded cost per accelerator-hour. Validate with production-like benchmarks; theoretical peak FLOPs are not a serving-throughput estimate.

### Designing for failure

Plan for tool timeouts, rate limits, malformed outputs, unavailable models, retrieval outages, stale data, and partial completion. Use bounded retries with backoff, idempotency where appropriate, circuit breakers, fallbacks, clear user messaging, and human escalation for consequential workflows.

### Safety boundaries

Define prohibited actions, allowed data, user consent, permission checks, human approval thresholds, and escalation paths. Enforce critical controls in application code and tool permissions—not only in prompts. Test adversarial inputs, prompt injection, data leakage, and unsafe tool use.

### Models improve; what stays constant?

Model capabilities and prices change quickly. Durable product work includes customer understanding, workflow integration, data quality and rights, trust, evaluation, security, distribution, reliability, and measurable business outcomes. Keep the architecture modular enough to change models without rebuilding the product.

## 6. Evaluation and metrics

### Build an evaluation framework from scratch

1. Define the user outcome and failure costs.
2. Identify representative tasks and segment them by risk and difficulty.
3. Create a versioned dataset of realistic inputs and expected properties.
4. Define rubrics for correctness, relevance, completeness, groundedness, safety, and style.
5. Combine deterministic checks, human review, and model-assisted evaluation.
6. Establish baselines and release thresholds.
7. Run offline evaluations, then shadow or limited production tests.
8. Monitor real-world quality, regressions, and user feedback continuously.

A benchmark score is not a substitute for observing whether the feature helps users complete their work.

### Precision, recall, and F1

- **Precision:** Of the items predicted positive, how many were actually positive?
- **Recall:** Of all actual positive items, how many did the system find?
- **F1:** The harmonic mean of precision and recall.

Use precision when false positives are costly; use recall when missing a relevant item is costly. Explain the trade-off in terms of user impact.

### LLM-as-judge

An LLM judge scores outputs against a rubric. It can scale evaluation, but may be biased by wording, verbosity, position, or model preferences. Validate it against human judgments, use clear rubrics and blind comparisons where possible, and audit disagreement. Do not use it as the sole authority for high-stakes decisions.

### Evaluating nondeterministic systems

Use repeated runs, distributions, confidence intervals, and task-level pass rates rather than expecting identical outputs. Track performance by scenario and segment. Preserve test inputs, model versions, prompts, tool versions, and evaluation configuration to make regressions diagnosable.

### Testing pyramid for AI products

- **Unit tests:** Deterministic code, schemas, permissions, parsing, and policy enforcement.
- **Component tests:** Retrieval, tools, prompt assembly, and model adapters.
- **Evaluation tests:** Golden datasets, adversarial cases, and repeated model runs.
- **End-to-end tests:** Full user workflows with real or representative dependencies.
- **Production monitoring:** Quality signals, user feedback, latency, cost, and incidents.

AI testing needs more evaluation and monitoring than a conventional deterministic application, but it still benefits from a strong base of fast deterministic tests.

### Model swaps and regression testing

A model swap can change formatting, tool selection, refusal behavior, latency, cost, and factuality. Run the same versioned evaluation suite against the old and new model, compare by task segment, and use shadow traffic or a gradual rollout with rollback criteria.

### Observability

Capture traces across the request: model/version, prompt template version, token counts, retrieval sources and scores, tool calls, latency, retries, errors, cost, and user feedback. Redact or minimize sensitive content and enforce access controls and retention policies. Observability should make it possible to locate which stage caused a quality or reliability drop.

### Human-in-the-loop feedback

Collect explicit ratings and corrections, but also look for behavioral signals such as edits, retries, abandonment, overrides, and acceptance. Make feedback actionable: connect it to a failure category, workflow stage, and evaluation case. Protect privacy and avoid treating every user action as ground truth.

### When offline evaluations pass but users are unhappy

Investigate whether the evaluation set represents real users, workflows, and edge cases. Check usability, trust, latency, freshness, coverage, discoverability, and whether the feature solves the actual problem. Segment feedback; an average score can hide a poor experience for an important cohort.

### Faithfulness versus retrieval quality

Retrieval quality asks whether the right evidence was found. Faithfulness asks whether the generated answer accurately reflects that evidence. Measure both independently: retrieval metrics can include recall@k and ranking quality; generation metrics can include claim support, citation correctness, and unsupported-claim rate.

### What to check first when quality drops

Check for recent changes in model/version, prompt, retrieval index, source data, tool behavior, traffic mix, and evaluation configuration. Use traces and segment-level metrics to isolate the stage and cohort affected before changing the model.

### How to answer company-style design questions

Use a consistent structure:
1. Clarify user, problem, scope, and constraints.
2. Define success metrics and unacceptable failure modes.
3. Describe the end-to-end architecture and data flow.
4. Explain model, retrieval, tool, and orchestration choices.
5. Cover latency, cost, reliability, privacy, and safety.
6. Explain evaluation, launch strategy, and iteration.

## 8. A technical AI PM answer framework

For almost any technical AI PM question, structure the answer around these lenses:

- **User problem:** Who is the user, what job are they trying to do, and why is AI useful?
- **Mechanism:** What happens under the hood, from input to output?
- **Alternatives:** Could rules, search, conventional ML, or a smaller model do the job?
- **Trade-offs:** What are the implications for quality, latency, cost, privacy, and complexity?
- **Failure modes:** How can the system fail, and how will users recover?
- **Evaluation:** How will you know it works across realistic scenarios?
- **Operations:** How will you monitor, secure, scale, and improve it?
- **Business outcome:** What measurable customer or business value does it create?

The strongest PM answers connect technical depth to product judgment. Avoid naming technologies without explaining why they fit the problem and what you would measure.

1. LLM fundamentals and model behavior.
2. Tool calling, agents, and MCP.

## Quick glossary

- **Grounding:** Tying an answer to trusted evidence or data.
- **Hallucination:** A plausible-sounding but unsupported or incorrect model output.
- **Inference:** Running a trained model to produce outputs.
- **Prefill:** Processing the input sequence before token generation.
- **Decode:** Generating output tokens sequentially.
- **Reranking:** Reordering retrieved candidates using a relevance model.
- **Redline:** A defined boundary beyond which a model or feature must not operate or be released.
- **SLO:** A target for a service-level indicator, such as latency or availability.
- **Non-determinism:** Variation in outputs or execution despite apparently identical inputs.
